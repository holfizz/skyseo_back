# SkySEO: сайт → анализ → клиентская презентация

Единая инструкция для Codex. Применять, когда пользователь присылает сайт и просит разбор или презентацию для созвона. Выполнить работу до готового PDF, а не ограничиваться планом. Эталон — актуальная презентация СКБ-4, согласованная пользователем. Изменять данные и персонализацию, сохранять оформление и порядок рассказа.

Достаточная команда пользователя: **«Собери презентацию для example.ru»**. Регион и приоритетные направления можно указать дополнительно. Результат — клиентский PDF в Downloads, отдельная PDF-шпаргалка по слайдам и проверяемые исходные данные в проекте.

## 1. Найти эталон и создать папку клиента

Рабочая директория: `skyseo_back/`. Перед началом прочитать корневой `AGENTS.md` и эту инструкцию.

| Назначение | Источник |

| Единый анализ, контрольные точки и очередь | `src/crm/preparation/pipeline.ts`, `preparation.service.ts` |

Создать `docs/clients/<client-slug>/`: безопасное имя из домена, без протокола, слешей и `..`. Исходный домен с зоной хранить в данных. Для PDF допустимы ссылки на источники; для любых сопроводительных Telegram-сообщений действует запрет полных доменов из `AGENTS.md`.

Сохранить `assets/`, `comparison/screenshots/`, `research.json`, `keywords-selected.json`, `positions-yandex-search-api.json`, `existing-visibility-probes.json`, `presentation-data.json`, `lead-opportunity-scenario.json`, `README.md`, PDF/HTML и шпаргалку. Не смешивать данные двух клиентов и не перезаписывать папку СКБ-4 при разборе другого сайта.

## 2. Понять бизнес по самому сайту

Открыть главную, каталог или услуги, контакты, 5–10 показательных товарных/сервисных страниц, `robots.txt` и доступные sitemap. Записать название компании, фактический ассортимент, услуги, города, бренды, модели и URL подтверждающих страниц. Сначала установить, что компания действительно продает или оказывает, затем подбирать запросы. Картинка или упоминание бренда сами по себе не доказывают предложение к продаже.

Регион взять из явно обозначенной географии бизнеса. Если несколько регионов и приоритет не очевиден — спросить одним коротким вопросом, продолжая изучать сайт. Не подставлять Москву всем клиентам. Если ответа нет, явно зафиксировать выбранный регион как допущение, использовать его одинаково для позиций и частот.

Скачать официальный логотип с сайта. Для обложки использовать отраслевое изображение в серой гамме; при необходимости сгенерировать отдельную иллюстрацию по правилам imagegen. Иллюстрация не должна выглядеть как доказательство результатов клиента. Не рисовать выдачу, графики позиций или скриншоты вместо измерений.

## 3. Собрать релевантные запросы и Wordstat

1. Из реальных разделов сайта выбрать 8–15 исходных тем: коммерческие категории, услуги, бренды и модели. Проверить каждую тему по странице клиента.
2. Через уже настроенный Wordstat собрать подсказки по этим темам в выбранном регионе. Локальная интеграция: `src/common/yandex-positions.ts`, endpoint XMLRiver `/wordstat/new/json`, параметры `query`, `regions` и `pagetype=words`; ответ содержит `popular` и `associations`. Читать только нужные настройки из локального `.env`, не печатать ключи и URL с секретными параметрами.
3. Отобрать до 100 уникальных полезных фраз. Предпочитать покупательские запросы и реальные товары. Удалить чужие ниши, вакансии, нерелевантные модификации и информационные фразы без связи с предложением. Не заполнять квоту мусором: если обоснованных фраз меньше, сохранить честное количество.
4. Для каждой фразы сохранить `keyword`, `group`, `sourceSeed`, `clientEvidenceUrl`, `volume`, регион, период и дату получения. Частоту брать только у совпадающей фразы, не у первого популярного результата. Ошибка/отсутствие частоты — `null` с причиной, не ноль.
5. Сохранить исходные ответы без секретов и список CSV/XML. XML корректно экранировать.

Широкая частота отражает запросы с фразой и ее формами; пересекающиеся частоты не складывать в число людей или заявок. Режим соответствия и период записывать из конкретной выгрузки. [Справка Wordstat](https://yandex.ru/support2/wordstat/ru/interface/new), [XMLRiver Wordstat](https://xmlriver.com/apiwordstatnew/apiwn-about/).

`scripts/fetch-presentation-wordstat.cjs` помогает получить частоты выбранных фраз, но исключает некоторые фразы со словом «цена» и не собирает все подсказки. Не использовать его как единственный источник ядра из 100 фраз.

## 4. Измерить позиции и найти существующую видимость

Основной метод — существующие локальные учетные данные `YANDEX_SEARCH_API_KEY` и `YANDEX_FOLDER_ID`. По каждой фразе получить органические результаты Яндекса для выбранного региона, сохранить первую десятку и позицию клиента в проверенной глубине. Проверять точный hostname и его поддомены; не сопоставлять просто подстроку. Рекламные блоки не считать органическими позициями.

Адаптировать метод из `scripts/fetch-skb4-yandex-positions.cjs`: заменить папку, домен, регион и входные фразы; не запускать исходный скрипт для другого клиента. Его кэш рассчитан на один замер: для нового замера создать отдельный файл, иначе старые даты и позиции останутся без обновления.

Рабочие параметры: `POST /v2/web/search`, `SEARCH_TYPE_RU`, нужный `region`, `GROUP_MODE_FLAT`, до 50 групп на странице, 1 документ, `FORMAT_XML`; ответ `rawData` декодировать из base64. Учитывать фактическое число документов, ошибки XML и HTTP. Ограничить параллельность двумя запросами, установить таймаут и конечное число повторов. При квоте/недостатке баланса остановиться, сохранить сделанное. [Официальная документация Search API](https://aistudio.yandex.ru/ru/docs/search-api/api-ref/WebSearch/search).

Каждая строка результата: `keyword`, `position` или `null`, ранжируемый `url`, `scanned`, `error`, `top10[{position,domain,url}]`, дата, регион и источник. «Не найден в топ-50» допустимо только при успешном ответе с 50 документами. Если просмотрено 37, писать про топ-37. Ошибку запроса не превращать в отсутствие сайта. API-срез не выдавать за одинаковую выдачу у всех пользователей.

Отдельно проверить 15–30 точных товарных, модельных и брендовых фраз, обнаруженных на сайте; метод — `scripts/probe-skb4-existing-visibility.cjs`, также с адаптацией под клиента. Это позволяет найти уже сильные позиции, когда широкие запросы не дают топ-50. Один запрос с названием компании использовать как контроль домена, не выдавать его за коммерческий успех.

На слайд выбрать 4 показательных коммерческих запроса: сильные позиции и реальные точки роста. Если топовых позиций нет, так и показать измеренные значения. Не создавать «предыдущие позиции» без прежнего замера. Полный фактический охват можно узнать из доступного владельцу Вебмастера и Метрики; без доступа не обещать полный список. [Статистика Вебмастера](https://yandex.ru/support/webmaster/ru/service/statistics).

## 5. Выбрать и проверить 2–3 конкурентов

Из сохраненного топ-10 выбрать компании с сопоставимым ассортиментом/услугами, регионом и типом бизнеса. Сохранить всю первую десятку в исследовании, в PDF показывать только полезные примеры. Агрегаторы, маркетплейсы, каталоги и одноименные компании отдельно классифицировать, не считать автоматически прямыми конкурентами.

Открыть конкретные страницы конкурентов из выдачи и соответствующие страницы клиента. Сделать реальные скрины и записать точные URL, дату, запрос, регион и позиции. Для адаптации скриншотов есть `scripts/capture-skb4-comparison.cjs`; его список URL относится только к СКБ-4.

Найти **два конкретных SEO-отличия**, которые можно применить к этому сайту: страницы под тип/модель/услугу, разделение спроса по посадочным, ссылки между разделами, полезные характеристики, соответствие заголовков и содержания запросу. Не делать основной аргумент из красивой кнопки, формы, цвета или чата. Ссылочная структура помогает роботу находить страницы; это полезный вывод, но не доказательство причины конкретной позиции. [Рекомендации Яндекса по структуре](https://yandex.ru/support/webmaster/ru/recommendations/site-structure).

Для каждого отличия записать во внутренние данные:

- что проверено у клиента и у конкурента, со ссылками;
- что можно применить с учетом реального ассортимента;
- какую SEO-задачу это решает;
- что осталось непроверенным.

Не писать «у клиента нет» по недоступной странице. Не утверждать «они выше только из-за этого». В клиентском PDF — простая формулировка наблюдения и действия; технические причины недоступности, CAPTCHA и незавершенные проверки остаются во внутреннем README. Если наблюдение проверить невозможно, выбрать другое доказуемое сравнение.

## 6. Объяснить пользу через расчет без вымышленных потерь

Выбрать 3–5 подтвержденных направлений. Сохранить частоты и расчет в `lead-opportunity-scenario.json`. Формула: спрос × условная доля переходов × конверсия в заявку; сделки = заявки × конверсия в сделку. Считать без промежуточного округления.

Если данных клиента нет, использовать только **условный сценарий**: 6%, 3%, 20% — допущения прежней модели, не отраслевые средние. Крупный заголовок слайда: **«Условный сценарий. Уточним по вашей аналитике»**. Не заявлять «вы теряете N заявок» и не суммировать пересекающиеся широкие частоты. Если частот нет, показать схему расчета без выдуманных цифр.

Если доступны подтвержденные данные Метрики/CRM, отметить их источник, период и сегмент и заменить допущения. Потери нельзя вычислить одним вычитанием условного сценария из несопоставимых текущих заявок. Без таких данных не превращать пример в прогноз.

Нейросети: не утверждать отсутствие продвижения или рекомендаций без отдельного исследования. Если проверять, сохранить список одинаковых вопросов, сервис, дату и полученные ответы; вывод относится только к этой выборке. Одна выдача не доказывает полную GEO-видимость или ее отсутствие. Общая услуга SkySEO допустима на слайде преимуществ без диагноза клиенту.

## 7. Собрать слайды в согласованном стиле

Использовать `clientCss` + **один общий модуль** `scripts/lib/client-presentation-style.cjs`, `clientSlide` и тот же рендер. Не копировать CSS в новый независимый дизайн. Не менять общие стили ради одного клиента без отдельного запроса. Эталон — актуальный HTML/PDF СКБ-4, а не старые универсальные отчеты.

Формат 297 × 167 мм; Helio из проекта; серый фон `#f2f2f1`, белые и серые скругленные блоки, темный текст; синий `#1d4e9e` только для акцентов. Допустим небольшой цвет логотипа клиента. Нет цен, макетов окна Mac, декоративных номеров 01/02, слешей, длинных объяснений, лишних линий, центрированных точек и подписи «Персональный разбор». Не добавлять `[·•⋮]` даже в подписи.

## 8. Единый механизм подготовки

Не создавать отдельный генератор или копию скрипта для каждого клиента. CRM и локальная подготовка используют `src/crm/preparation/pipeline.ts`, один адаптивный шаблон `src/report/call-presentation.template.ts` и один `buildCallScript` для UI и PDF. Старые `build-skb4-*` оставлены только как история ручного эталона; новые материалы собирать универсальной командой.

```sh
npm run prepare:call -- --site example.ru --name "Название компании" --region Москва --limit 40 --out docs/clients/example/prepared-call
```

Допустимый лимит 8–100. `--keywords файл.json` добавляет только исходные фразы: старые числа не становятся новым замером. Для явно подтвержденного специалистом бесплатного теста добавить `--trial confirmed`; иначе следующий шаг — проверка применимости теста. `--trial unavailable` предлагает индивидуальный план. Не обещать тест автоматически любому сайту.

Возобновление без повторения успешных замеров:

```sh
npm run prepare:call -- --site example.ru --region Москва --out docs/clients/example/prepared-call --resume --retry-phase POSITIONS
```

Этапы: SITE, KEYWORDS, POSITIONS, COMPETITORS, DOCUMENTS. Файл `research.json` сохраняется после каждой страницы и замера; рядом сохраняются `slides.json`, `call-script.json`, клиентские `CLIENT_PRESENTATION.pdf/html` и `CALL_SCRIPT.pdf/html`. `--resume` проверяет совпадение домена и региона. Повтор DOCUMENTS сохраняет уже готовый клиентский PDF; чтобы применить изменение шаблона, удалить только его локальную копию и повторить DOCUMENTS. Данные и замеры не удалять.

В CRM: карточка лида → «Подготовить созвон». Очередь хранит материалы в `CrmCallPreparation`, а не в полях ответов клиента. Один активный job на лид, транзакционная постановка, lease с восстановлением после перезапуска, отдельная версия после повторной подготовки. Статусы PENDING/RUNNING/READY/PARTIAL/FAILED. Ошибка одного источника не превращается в нулевую позицию или частоту. PARTIAL означает готовые документы с явно неполными источниками; служебные причины видны оператору, а неподтвержденные слайды исключены из клиентского PDF.

Публичный анализ ограничен размером страниц, количеством ресурсов, временем и числом запросов. Внутренние IP, локальные адреса и URL с учетными данными запрещены, DNS-адрес проверяется и закрепляется при подключении. Не обходить CAPTCHA. Не отправлять формы клиента или конкурента. Не подключать Telegram для анализа сайта.

Wordstat: XMLRiver `regions=<код региона>`, `pagetype=words`; `lr` относится к поиску Яндекса и не подменяет фильтр Wordstat. Частота сохраняется с датой, регионом и типом соответствия. Search API HTTP 429 прекращает новые замеры этой партии после ограниченного повтора; не переключать аккаунты или ключи для обхода лимита. При недоступном Wordstat нет слайда с придуманным спросом. Регионы «Москва» не подставлять всем клиентам; неизвестный выбор отмечать допущением.

Данные исследования: точные URL, title/заголовки/содержимое, ссылки с отделением меню, реальные скриншоты и время; фразы с URL подтверждающей страницы; позиция либо отсутствие в конкретной проверенной глубине, дата/регион/источник/top-10; частота либо null; наблюдения по клиентской и конкурентной странице. Сравнивать сопоставимые товарные страницы, а не общий футер. Одинаковые элементы не доказывают преимущество. Если конкретное отличие не подтверждено, сравнение исключить. Сохранять реальные даты старых повторно используемых замеров: не датировать их сегодняшним числом.

## 9. Один сценарий для выступления, CRM и PDF

Текст строится `buildCallScript(context, null, {research, slides})`. Номер слайда определяется по его ID в итоговом outline, а не жесткой константой. Пропуск неподтвержденного слайда автоматически меняет номера во всех материалах. Кейс, преимущества и портфолио — отдельные этапы.

Манера: «Здравствуйте! Как у вас дела?», «Смотрите, вот что удалось найти», «Давайте покажу еще один пример». Короткие разговорные абзацы, конкретные данные, без лозунгов и канцелярита. Никакого повторного согласования 15 минут на уже согласованном созвоне. Не переносить числа СКБ-4 на другого клиента. Не обещать рост по всем запросам, рекомендации нейросетей или фактические потерянные заявки.

До разбора: кто занимается SEO, бизнес-задача, приоритетные направления. После находок: актуальность решений и данные о заявках, если есть проверенный спрос. После кейса/преимуществ/портфолио: интерес, бюджет, следующий шаг. Ответы, которые уже есть в квалификации, не спрашивать повторно. При ответе «SEO нет» вопросы о подрядчике и его результате не показывать. Вопрос о ЛПР не возвращать.

UI показывает один этап и один вопрос: крупное «Скажи», «Спроси», кнопки или поле «Ответ», Назад/Далее. Дополнительные вопросы, заметка и подсказки свернуты. Одна ситуация в подсказке одновременно. Предпросмотр слайда включается по желанию. Alt+стрелки работают вне полей ввода. Ответы, комментарии и курсор этапа сохраняются на сервере, сбой сохранения не позволяет молча закрыть или перейти дальше. Следующий контакт создает `CrmTask(FOLLOW_UP)` и `CrmReminder` через общий FollowUpService; legacy Telegram поля синхронизируются только при связанном диалоге.

PDF ведущего использует этот же сценарий, шрифт основного текста 14 pt и естественную пагинацию. Не сжимать его до двух страниц ценой читаемости. Известные вопросы и неактуальные условные вопросы исключаются. После записи ответов скачивание обновляет сценарий по текущей CRM.

## 10. Проверить и доставить

Перед выдачей:

- Все позиции, конкуренты, частоты и даты сверены с источниками; цифры из другого клиента не остались. Нет выдуманного прошлого замера или диагноза GEO.
- Оба скрина кейса загрузились, порядок и хэши верны, второго кейса и пустых мест нет. Изображения не растянуты; фрагменты не меняют числа и даты.
- Открыть PDF и отрендерить измененные страницы в PNG через `pdftoppm`. Проверить глазами обложку, оба сравнения, расчет, кейс и коллаж.
- В браузере проверить границы слайдов и карточек, переносы текста, шрифты, `img.complete`/`naturalWidth`. Обрезка разрешена только у явно заданных фрагментов скринов; текст не должен обрезаться.
- Через `pdfinfo` проверить число страниц, через `pdftotext` наличие всех выбранных фраз, отсутствие служебных ремарок и лишних точек. Сверить номера в шпаргалке. Число страниц зависит от подтвержденных данных. Проверить фактический outline и естественную пагинацию сценария; не навязывать фиксированное число страниц.
- Ссылки портфолио ведут к полным существующим публичным картинкам; данные API и ключи не попали в HTML, PDF, изображения или логи.

Экспортировать **сначала шпаргалку, затем презентацию**, чтобы клиентская презентация оказалась сверху в Downloads при сортировке по дате. Только через помощник:

```sh
node scripts/export-pdf-to-downloads.cjs docs/clients/skb-4/SKYSEO_SKB-4_CALL_NOTES.pdf SkySEO_SKB-4_CALL_NOTES.pdf
node scripts/export-pdf-to-downloads.cjs docs/clients/skb-4/SKYSEO_SKB-4_PRESENTATION.pdf SkySEO_SKB-4_2026-10-13.pdf
```

Для нового клиента подставить его пути и имя. Помощник обновляет дату в датированном имени на текущую московскую дату, создает новый файл и заменяет прежнюю копию со свежими creation/mtime. Даты замеров внутри документа сохраняются. Проверить SHA-256 копии против проектного PDF и обе файловые даты.

В конце дать ссылки на клиентский PDF и шпаргалку, кратко назвать количество запросов, регион и реальную дату замера. Если данных недостает, прямо назвать это и отделить черновик от готового разбора. Самостоятельно не отправлять PDF клиенту, не менять его сайт, не запускать рассылку и не переносить секреты/сессии на сервер. Для подготовки по публичному URL не требуются изменения прод-БД.
